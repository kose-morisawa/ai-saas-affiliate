## SSH接続の設定：エックスサーバーとConoHa WINGで何が違うか

ここから本題のエンジニア向けセクションです。まずSSH。ここの差は、ほとんどの比較記事で一切触れられていません。

### エックスサーバーのSSH設定手順：公開鍵認証のみ対応・ポート10022

エックスサーバーは**パスワード認証に非対応で、公開鍵認証のみ**です。接続ポートは10022に固定されています。

<cite><a href="https://www.xserver.ne.jp/manual/man_server_ssh.php" target="_blank" rel="nofollow noopener">エックスサーバー SSH設定マニュアル（アクセス日：2026-05-29）</a></cite>

鍵の用意は2択で、サーバーパネル上で鍵ペアを自動生成して秘密鍵をダウンロードするか、自分のマシンで`ssh-keygen`した公開鍵を手動登録するかです。私はGitHub Actions連携を見据えて後者でやりました。接続コマンドはこんな感じになります。

```bash
# 自分で鍵を生成して公開鍵をサーバーパネルに登録した場合
ssh -i ~/.ssh/xserver_key -p 10022 your_account@svXXXX.xserver.jp
```

### ConoHa WINGのSSH設定手順：SSHアカウント作成・専用ポート番号の確認

ConoHa WINGは少しクセがあって、**管理パネルでまずSSHアカウントを作成**します。そしてアカウントごとに異なるポート番号が割り当てられる仕組みです。10022固定ではないので、接続前に必ず管理画面でポート番号を確認する必要があります。

<cite><a href="https://support.conoha.jp/w/sshaccount/" target="_blank" rel="nofollow noopener">ConoHa WING サポート SSHアカウント（アクセス日：2026-05-29）</a></cite>

```bash
# 管理パネルで確認したポート番号を指定
ssh -i ~/.ssh/conoha_key -p <割当ポート番号> <SSHユーザー名>@<ホスト名>
```

### 両者のSSH接続を比較：鍵管理・接続安定性・複数アカウント運用

| 観点 | エックスサーバー | ConoHa WING |
|---|---|---|
| 認証方式 | 公開鍵のみ | 公開鍵 |
| ポート | 10022固定 | アカウント別に動的割当 |
| 複数ユーザー運用 | サーバーアカウント単位 | SSHアカウントを複数作成可 |
| 設定難易度 | 中（鍵登録のみ） | やや高（アカウント作成が一手間） |

複数の開発者で1サーバーを共有する場合、SSHアカウントを個別に切れるConoHa WINGのほうが権限分離しやすいです。一方、ポートが固定で覚えやすいエックスサーバーは、踏み台スクリプトや`~/.ssh/config`の管理が楽。このあたりは運用スタイル次第ですね。

## Node.jsのデプロイ：glibcの壁とその回避策

さて、エンジニアが一番ハマるのがここです。**glibcの壁**。

### エックスサーバーのglibc制約：CentOS7ベース・glibc 2.17の現実

エックスサーバーをはじめ多くの国内レンタルサーバーはCentOS 7系がベースで、システムのglibcが2.17のままなんです。ところが**Node.js公式のLinuxバイナリはglibc 2.28以上を要求します**。つまり`nvm install 22`で素直に入れても、いざ実行すると`GLIBC_2.28 not found`みたいなエラーで起動しません。これがコミュニティで延々と話題になる地雷です。

### Node.jsの最新版をエックスサーバーで動かす方法：unofficial builds活用

回避策は、Node.jsの**unofficial builds**（glibc 2.17向けにビルドされた非公式バイナリ）を使うことです。具体的には、nvmのミラー環境変数を上書きしてインストールします。

<cite><a href="https://qiita.com/saizeriiya/items/c68d77b01a69c97bb311" target="_blank" rel="nofollow noopener">Qiita：エックスサーバーでのNode.js導入とglibc回避策（アクセス日：2026-05-29）</a></cite>

```bash
# nvmのミラーをunofficial buildsに切り替えてインストール
export NVM_NODEJS_ORG_MIRROR=https://unofficial-builds.nodejs.org/download/release
nvm install 22  # x64-glibc-217 バイナリが取得される
node -v
```

このひと手間を知っているかどうかで、エックスサーバーでのNode.js体験は天と地ほど変わります。

### ConoHa WINGでのNode.js環境構築：portable-node方式の手順

ConoHa WINGも共有環境のglibcは古いので、結局ここでも同じ壁にぶつかります。こちらはportable-node（ポータブル版バイナリを展開してPATHを通す）方式が定番。基本的な考え方はエックスサーバーと同じで、「OSのglibcに依存しないNode.jsを自前で用意する」という発想です。要は、どちらを選んでもglibcとは一度は向き合うことになります。

### どちらが開発体験が良いか：nvmとpyenv対応状況の比較

| 項目 | エックスサーバー | ConoHa WING |
|---|---|---|
| nvm | 利用可（ミラー上書きで最新版） | 利用可（portable推奨） |
| pyenv | 利用可（ビルド依存に注意） | 利用可 |
| glibc回避の手間 | ミラー環境変数1行 | portable展開 |

結論、Node.js導入の手軽さは**ミラー1行で済むエックスサーバーがわずかに楽**だと感じました。とはいえどちらも「公式バイナリそのままは動かない」という前提は同じです。

## Python・AI開発での利用：LLM APIサーバーはどちらに向くか

次はPythonとAI開発。ここも競合記事がほぼ扱っていない領域です。

### エックスサーバーでPythonを動かす：pipとvenvの制約

両者とも`pyenv`でPythonを入れ、`venv`で仮想環境を切るのは可能です。ただ共有環境なのでビルドに必要なヘッダやコンパイラが揃わずソースビルドでコケることがあります。ホイール（wheel）が配布されているパッケージを優先するのがコツです。

### Flask/FastAPIのデプロイ：.htaccessリバースプロキシ設定

レンタルサーバーは基本的にApacheやLiteSpeedが80/443を握っているので、FlaskやFastAPIは内部ポート（例：8000）で起動し、`.htaccess`のリバースプロキシで外部リクエストを転送する構成になります。Zennの実践記事でも、NestJSアプリをPM2で常時起動させ`.htaccess`でプロキシする手順が紹介されています。

<cite><a href="https://zenn.dev/hiro_ghap1/articles/1e0b67c6f44660" target="_blank" rel="nofollow noopener">Zenn：エックスサーバーへのNestJSデプロイとPM2活用（アクセス日：2026-05-29）</a></cite>

### AI APIサーバー（OpenAI Proxy・LLMラッパー）のホスティング可否

「OpenAIのプロキシやLLMラッパーを動かしたい」という需要、ありますよね。技術的にはPM2 + リバースプロキシで動かせますが、共有環境なので**長時間のストリーミング接続やWebSocket、重いメモリ消費には向きません**。軽量なAPIラッパー程度なら動きますが、本気のAIバックエンドには厳しいというのが正直なところです。

なお、エックスサーバーは2026年4月16日に「XServer API」の提供を開始し、API経由でサーバー操作の自動化が可能になりました。これは運用自動化を組みたいエンジニアには地味に大きなアップデートです。

### レンタルサーバーの限界：共有環境でのポート制限とVPSへの移行判断

ルートポート（80/443）を直接握れない、常時起動プロセスにリソース制限がかかる、といった共有環境の限界に当たったら、それはVPSへの移行サインです。本格的なAPIサーバーやモデルホスティングなら、最初から従量課金のクラウドやVPSを選んだほうが結局コスパが良いです。

## GitHub Actionsで自動デプロイ：CI/CDパイプラインの構築方法

ここがエンジニアにとっての本丸、CI/CDです。

### エックスサーバーへのGitHub Actionsデプロイ：rsync + SSH Secretsの設定

GitHubリポジトリのSecretsに`SSH_HOST`・`SSH_PORT`・`SSH_USER`・`SSH_KEY`（秘密鍵）を登録し、ビルド成果物をrsyncで転送するのが王道です。エックスサーバーはポート10022固定なので、`SSH_PORT`に10022を入れます。

```yaml
name: Deploy to Xserver
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci && npm run build
      - name: Setup SSH key
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.SSH_KEY }}" > ~/.ssh/id_rsa
          chmod 600 ~/.ssh/id_rsa
      - name: rsync deploy
        run: |
          rsync -avz --delete -e "ssh -p 10022 -i ~/.ssh/id_rsa -o StrictHostKeyChecking=no" \
            ./dist/ ${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}:~/public_html/
```

### ConoHa WINGへのGitHub Actionsデプロイ：sftp-deployとrsyncの選択

ConoHa WINGはSSH Secretsを登録したうえで、rsync・scp・lftp・gitの4方式から選べます。ポートはアカウント別なので`SSH_PORT`にその番号を入れるのを忘れずに。

<cite><a href="https://zenn.dev/su8ru/articles/deploy-to-conoha-wing" target="_blank" rel="nofollow noopener">Zenn：GitHub ActionsからConoHa WINGへのデプロイ4方式（アクセス日：2026-05-29）</a></cite>

```yaml
      - name: rsync deploy to ConoHa WING
        run: |
          rsync -avz --delete \
            -e "ssh -p ${{ secrets.SSH_PORT }} -i ~/.ssh/id_rsa -o StrictHostKeyChecking=no" \
            ./dist/ ${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }}:~/public_html/
```

### Astro/Next.js/Nuxtのビルド成果物を転送する実践的なワークフロー例

このサイト自体もAstro製なんですが、Astroは`npm run build`で`dist/`に純粋な静的ファイルを吐くので、レンタルサーバーとの相性は抜群です。Next.jsのSSGやNuxtのgenerateも同様に、静的成果物だけを`public_html`に転送すれば動きます。逆に、Next.jsのSSR（サーバーサイドレンダリング）はNodeプロセスの常時起動が必要なので、レンタルサーバーではかなり苦しくなります。

### デプロイ速度・安定性の比較：転送エラーの発生頻度

体感では、rsyncの差分転送を使えばどちらも安定しています。両者ともSSHの接続安定性は十分で、転送エラーはほぼ出ませんでした。`--delete`を付けると削除されたファイルも同期されるので、ゼロダウンタイムに近い更新ができます。

## 実際に使ってみた：エックスサーバーにAstroサイトをデプロイした話

ここからは私の体験談です。このブログ（あふぃプロジェクト）の本番環境候補として、実際にエックスサーバーにAstroサイトをデプロイして検証しました。

### 試した構成：Astro + GitHub Actions + rsyncでのゼロダウンタイムデプロイ

構成はシンプルで、`main`にpushしたらGitHub ActionsでAstroをビルドし、`dist/`をrsyncで`public_html`へ転送するというもの。最初はすんなりいくと思っていたんですが、見事に2回ハマりました。

### つまずいたポイント1：glibc制約でnpm buildが通らなかった

最初の失敗は、サーバー上でビルドしようとしてglibc制約に激突したこと。`nvm install`した最新Nodeが`GLIBC_2.28 not found`で起動せず、npm buildどころかnodeコマンド自体が動きませんでした。「これか、噂のglibc地獄は……」と、しばらく画面の前で固まってました。

結局、ビルドはGitHub Actionsのubuntu-latest側で完結させ、サーバーには静的成果物だけ送る方針に切り替えて解決。そもそもサーバーでビルドしなければglibcは関係ないわけです。サーバー側でNodeを動かす必要があるなら、先述のミラー環境変数で回避できます。

### つまずいたポイント2：SSH鍵のパーミッション設定ミスで接続失敗

2つ目の失敗は超基本的なやつで、お恥ずかしい。GitHub Actionsで秘密鍵をファイルに書き出したあと、`chmod 600`を入れ忘れて`Permissions 0644 are too open`で接続拒否されました。SSHは鍵のパーミッションに厳しいので、`chmod 600 ~/.ssh/id_rsa`は必須です。これ、ローカルだと自動で正しい権限になるので、CI環境で初めて踏みがちな罠なんですよね。

### 解決後の使用感：デプロイ時間・安定性・管理パネルの使いやすさ

2つの壁を越えたあとは快適でした。rsyncの差分転送なので2回目以降のデプロイは数秒で完了し、安定性も文句なし。管理パネルも国内サービスらしく日本語で分かりやすかったです。

ただ最終的に、私はこのブログをCloudflare Pagesに置くことにしました。静的サイトならグローバルCDNで配信できるPagesのほうが速くて、無料枠も大きいからです。エックスサーバーが悪いわけではなく、単に「静的サイトを置くだけ」という今回の用途とは相性の問題ですね。とはいえ「どうしてもPHP/WordPressやリバースプロキシが必要」というエンジニアには、エックスサーバーは堅実な選択肢だと実感しました。

## エックスサーバー・ConoHa WINGのメリット・デメリット【エンジニア視点】

検証を踏まえて、エンジニア視点でのメリット・デメリットを正直にまとめます。

### エックスサーバーのメリット5選：国内No.1シェア・安定稼働・XServer API対応

1. 国内シェア上位で運用実績が長く、安定稼働の安心感がある
2. NVMe SSDを全プランで採用していてI/Oが速い
3. ポート10022固定でSSH設定がシンプル
4. 2026年4月開始のXServer APIで運用自動化が組める
5. 独自ドメイン永久無料など長期運用の特典が手厚い

### エックスサーバーのデメリット3選：glibc古い・Node.js最新版非対応・料金が初年度と2年目で異なる

### ConoHa WINGのメリット5選：管理パネルのUI・WEXAL高速化・vCPU/メモリのスペック優位

1. 管理パネルのUIが新しく直感的に使える
2. メモリ・vCPUが数値で明示されていて選びやすい

## こんなエンジニアにはこちらがおすすめ

最後に、タイプ別の明快な結論を出します。

### エックスサーバーが向くエンジニア：WordPress管理・長期安定運用・XServer API活用

既存のWordPressサイトを運用していて、それと並行してAPI連携や軽いNodeツールを動かしたい人。3年スパンで腰を据えて運用したい人。XServer APIで運用を自動化したい人。このタイプはエックスサーバーが堅実です。

### ConoHa WINGが向くエンジニア：新規スタート・メモリ重視・管理UIの使いやすさ

これから新規で始める人。ポートフォリオや静的サイトを置きたい人。メモリ・vCPUを数値で確認して選びたい人。管理画面の使いやすさを重視する人。このタイプはConoHa WINGが快適です。

### どちらも向かないケース：常時起動バックエンド・WebSocket・LLMモデルのホスティング

WebSocketを常時張る、LLMモデルをホストする、重い常時起動バックエンドを動かす——こうしたケースは**両者とも向きません**。素直にVPS、もしくは静的フロントはCloudflare Pages・バックエンドは別途クラウドという分離構成を選びましょう。レンタルサーバーに無理をさせると、結局運用で消耗します。

## まとめ：エンジニアのサーバー選びで本当に重要な3つのポイント

### エンジニア視点のサーバー選び3原則：glibc確認・SSH認証方式・CI/CD対応

長くなったので3原則に圧縮します。**1つ目はglibcのバージョン確認**（Node.js最新版を動かすなら必須）、**2つ目はSSH認証方式とポートの把握**（エックスサーバーは10022固定・公開鍵のみ、ConoHa WINGはアカウント別ポート）、**3つ目はGitHub Actionsでrsyncデプロイが組めるか**。この3つを押さえれば、ブログ向けの比較記事に振り回されずに自分に合ったサーバーを選べます。

### よくある質問（FAQ）

**Q. エックスサーバーでNode.js 22は動きますか？**
A. そのままの公式バイナリはglibc 2.17制約で動きません。`NVM_NODEJS_ORG_MIRROR`をunofficial buildsに切り替えてx64-glibc-217バイナリを使えば動きます。

**Q. ConoHa WINGでPM2は使えますか？**
A. SSHで接続してNode環境を整えればPM2による常時起動管理は可能です。ただし共有環境のため、重い常時起動プロセスには向きません。

**Q. GitHub ActionsからSSHデプロイするとき必要なSecretsは？**
A. 一般的には`SSH_HOST`・`SSH_PORT`・`SSH_USER`・`SSH_KEY`の4つです。エックスサーバーはポート10022、ConoHa WINGはアカウント別ポートを`SSH_PORT`に設定し、CI上では秘密鍵に`chmod 600`を忘れずに。
